# 组件指导与审查工作流

本文是两模式共用的执行事实源，[workflow.svg](../docs/workflow.svg) 是人类概览。组件规范从 AaronUI-Web 本地知识 MCP 读取，精确 API 与行为按当前 TypeScript 实现核实，本 Skill 不维护规范副本。

## 1. 选择模式与范围

| 模式 | 用途 | 继续读取 |
| --- | --- | --- |
| `guidance` | 设计、选型或实现前，依据任务、当前规范和真实组件能力给出可实施用法与验证计划 | [guidance](guidance.md) |
| `audit` | 对已有界面、设计或实现核对组件选择、组合和内部用法；后续改动只复核受影响部分 | [audit](audit.md) |

- 混合请求先指导后审查，分别记录建议与实际证据。仅颜色、间距等视觉问题按原请求处理，不扩张为本专项。
- 任务审查或实现可交互 Dialog / Sheet 的行为时，两模式都读 [动效专项](dialog-motion.md)；仅文案局部取证不读取无关动效资料。
- “编辑 Reference / 同步索引”不是本包职责：规范由 AaronUI-Web 维护。用户明确授权修改源项目时按源仓规范完成，否则只给源位置。

沿用已有任务、目标工程和授权。以真实调用方确认组件，稳定 ID 不等于展示名或导出名，不能靠外形匹配。只读审查不授权修改产品、组件库或规范；已有具体实施授权则完成其范围内修复及验证。

## 2. 取得规范与能力证据

按 [知识访问契约](knowledge-access.md) 调用 MCP：`list_documents` 定位资料与章节 ID，`get_document` 只请求相关章节。同一任务内未变化的证据可复用；跨会话、规范变化或影响判断的实现变化后重新获取并标记基线。基线记录实际可得的服务版本、资料链接/ID、章节、读取时间及目标实现；revision 仅在服务提供时记录，不自造。

记录来源、可得版本、章节及实现版本，报告只引用判断所需短片段。规范覆盖以当前服务目录为准：不支持的资源记**未覆盖**；服务不可用、读取失败、来源无法核实或与源码冲突记**待验证**及最小缺失证据。继续不依赖它的部分，核心判断依赖它时暂停该结论。不读取旧 checker、其他 Skill 的静态规则或相似组件规则兜底，不擅自安装或启动服务。

规范决定语义、使用条件与组合；TypeScript 类型、导出和实现决定 props、回调、默认值与行为；业务决定以最新有效需求为准。来源冲突时说明影响，不静默改任何一方。源码存在不证明运行行为。

### 组件文案的局部取证

wording 调用本路径时，由当前执行者承担 advisor 取证职责，范围限于本次组件文案判断，不默认启动完整 guidance / audit、Example 全目录审阅或动效测试。

1. 核实目标的真实组件与场景、各文本角色和动作后果。先检查本任务 advisor 已取得的原始证据：资料链接/ID、章节、适用条件、完整相关规则、读取基线均可追溯，且源与目标语义未变化时复用，不重复查询。只有结论摘要、相邻场景证据或无法确认仍有效时补查。
2. 按 [知识访问契约](knowledge-access.md) 发现实际组件及关联 Wording Docs，读取相关组件章节与适用 Doc 的显式规则。关联元信息不等于规则正文；组件未列关联时，以任务语义搜索或浏览 Wording 分组，空搜索不证明无规则。只读本次相关资料，不扩展到全部 Docs。
3. 输出规则适用范围、目标角色映射、来源及证据状态，交 wording 做中文改写。组件或 Doc 均未覆盖该判断时，才可将内置规则作为明确标注的默认建议；尚未查询、工具不可用或响应失败时不能这样替代。涉及组件选择、配置、职责或组合变化时，按已授权范围进行局部 guidance / audit；否则到文案取证为止。

### Example 发现与读取

1. `list_examples` 分页读到 `nextCursor=null` 得到完整目录；第一页或关键词结果不算完整目录。
2. 按任务、页面与组件范围选择参考，用 `get_example` 读取源码、CSS、依赖与附加规则；需要更多文件时只从 `implementation.availableFiles` 选路径补读，核对 `context.unreturnedFiles`。
3. 没有明显候选时，分批读完本次组件范围内**全部** Example 实现后才能认定无适用参考；逐项记录已读/未读，读取失败的保留为待验证。
4. 记录选择理由、来源/可得版本、规则读取状态、读取范围和与需求的差异。目录摘要不能代替实现阅读。

可参考与可直接移植分开判断：未经移植验证或依赖 Gallery 上下文的源码仍可参考；直接移植须核实目标依赖、公开 API 与环境差异。`source-reference` 只表示需要适配依赖，不代表需要重新设计。

## 3. 来源优先级

1. 用户真正明确的要求，包括逐字指定的文案或明确批准的规则例外；
2. 项目成文约定与适用的当前组件规范、关联 Docs、匹配 Example 的明确规则及结构，共同核对适用范围；
3. PRD / 简报中的未明确指定措辞、AI 提案及 wording 内置默认规则，只补足上层未覆盖的部分。

PRD 说明业务事实和动作后果，但业务行为要求不自动指定标题或 CTA。PRD 中确属用户明确要求的内容按第 1 层处理；不能仅因文件名是 PRD 或方向获批就将全部文案提升为用户要求。适用组件/Doc 规则覆盖通用 G 类默认值时采用专属规则并注明依据。项目约定、组件规范、关联 Doc 或 Example 在同一适用范围真实冲突时，列双方具体规则、影响与可独立处理部分；未明确的取舍保持待验证并请求解决，不静默选一方或虚称一致。已明确授权的例外直接沿用并记录偏离。

## 4. 证据状态

取得过程与合规结论分开记录：**尚未查询**是没有发起必要读取；**MCP 不可用 / 未暴露**是已检查宿主工具或连接但无法调用；**规则未覆盖**须有已读目录及相关正文支持；**响应失败**须保留实际错误与未读范围。这些状态不能互相替代。尚未查询先按授权查询；不可用或失败时继续独立工作，相关结论待验证，不声称“查询无结果”或“已验证”。

| 状态 | 所需依据 |
| --- | --- |
| 符合 | 规则适用，且有足够当前证据；说明静态或运行证据范围 |
| 违例 | 当前证据与适用规则冲突，能解释对任务的影响 |
| 待验证 | 已有规则覆盖，但缺运行/业务证据或来源冲突未解 |
| 未覆盖 | 当前知识服务不支持对应资源或规则；不算符合 |
| 不适用 | 规则前提在本场景不成立，并给出理由 |

静态图、截图、一次成功操作或公开 API 合法都不能证明其他状态或动态行为通过；未观察到某行为不直接判违例。

## 5. 完成与交接

小任务在会话交付；需要跨阶段追踪时用目标项目已有报告位置或 `docs/design/<topic>/`，不写入本 Skill。至少保留模式、目标基线、规范来源/可得版本/章节、Example 选择与已读/未读、证据、结论/改动、未覆盖与待验证项。

完成意味着约定范围内每个对象有结论或明确的覆盖/证据缺口，已授权改动和相关验证已处理。可以交付“含未覆盖项的指导/审查”，不能称所有组件合规。关键证据无法获取时报告阻塞与已完成部分。交回调用方时只带报告位置、基线与受影响项；组件审查不替代信息、流程、走查或文案审查，也不越过它们的人工 Review。
