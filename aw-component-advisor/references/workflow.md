# 组件指导与审查工作流

本文是执行事实源，[workflow.svg](../docs/workflow.svg) 是人类概览。本 Skill 保存工作方法；组件规范从 AaronUI-Web 的本地知识 MCP 读取，精确 API 与行为按当前 TypeScript 实现核实，不在 Skill 中维护规范副本。

## 1. 选择模式与范围

- **guidance**：准备设计、选型或实现时，依据用户任务、当前规范和真实组件能力给出可实施的用法与验证计划。完整设计流程在塑形之后、生成初版之前执行。
- **audit**：对已有界面、设计或实现核对组件选择、组合和内部用法。完整流程在信息冗余审计之后执行；后续改动改变组件用法或约束时，只复核受影响部分。
- 混合请求先指导后审查，分别记录建议与实际证据。仅颜色、间距等视觉问题按原请求处理，不扩张为本专项。
- 旧“编辑 Reference / 同步索引”请求不是第三种模式：指出规范由 AaronUI-Web 维护，不能在本包恢复静态 Reference。若用户明确授权修改该源项目，按源仓规范完成；没有该授权时只给源位置与迁移说明。

沿用用户已给出的任务、目标工程和授权。识别本次对象、触发入口、当前状态和期望结果，以真实调用方确认组件。稳定 ID 不等于展示名或代码导出名；不能靠外形匹配。只读审查不自动授权修改产品、库组件或规范，已有具体实施授权则完成其范围内修复及验证。

## 2. 获取同一规范与能力证据

读取 [知识访问契约](knowledge-access.md)，通过 `list_documents` 定位当前资料与真实章节 ID，再用 `get_document` 请求相关章节；使用 v3 envelope 和发现所得 revision，不沿用 v1 全文调用。Example 按下述流程发现与读取，规范仍只读取相关章节与必要的真实源码。已经取得当前版本且没有相关变更时可在同一任务内复用；跨会话、规范变化或影响判断的实现变化后重新获取并标记基线。

guidance 与 audit 使用同一份规范。记录文档来源、revision、章节/规则引用及实现版本，报告只引用判断需要的短片段，不保存一份供下次执行使用的规范副本。历史报告保留当时证据，不能升级为当前规范。

规范覆盖与 Example 可参考范围分别以当前服务目录为准，不固定组件或业务场景 ID。Example 源码可供参考不等于它具有独立规范覆盖或通过移植验证。服务不支持对应规范时记录**未覆盖**，禁止读取旧 checker、其他 Skill 的静态组件规则、历史 Gallery 文案或相似组件规则兜底；依赖组件可按真实导出和类型组合，但不虚称独立规范已覆盖。

服务不可用、正文缺失、响应不能核实来源、读取失败，或资料与当前源码发生影响判断的冲突时，记录**待验证**及最小缺失证据。继续不依赖它的部分；核心判断依赖该资料时暂停相应结论，不把工具错误或空结果算成功。不擅自安装、启动服务或改客户端配置，用户已有授权时可按服务文档操作。不能用缓存或内置规则制造通过。

规范用于语义、使用条件与组合判断；当前公开 TypeScript 类型、导出和实现用于精确 props、回调、默认值与行为判断。业务决定以最新有效需求为准。来源冲突时说明冲突及影响，不静默改任何一方来制造一致；源码存在也不能证明运行行为通过。

### Example 发现、选择与读取

先通过 `list_examples` 读取 Gallery 当前 Example 的完整目录，持续读取分页直到 `nextCursor=null`；不能把第一页、关键词检索结果或被自行筛成可移植的子集当作完整目录。目录由 Gallery 当前 Example 数据与实现自动生成，新增 Example 不应要求 MCP 手工登记业务场景、增加工具参数或专属分支；Skill 不维护静态目录或场景名单。

结合任务、页面与组件范围，从完整目录选择值得参考的 Example，再通过通用 `get_example` 请求其详细源码、CSS、依赖索引、同源附加规则及必要上下文；只从详情的 `implementation.availableFiles` 选择路径，用 `files` 每次补读最多 30 个唯一文件，并核对 `implementation.context.unreturnedFiles` 与依赖索引，不能将路径参数用于任意文件访问。记录选择理由、来源/revision、规则正文与适用范围的读取状态、读取范围和与目标需求的差异。无附加规则须有当前服务明确证据；规则字段缺失、正文读取失败或版本无法核实均为待验证，不能当成无规则。目录摘要不能代替实现阅读；实际字段和筛选参数按当前服务契约使用。

若目录没有明显候选，先明确本次组件范围，再分批读取该范围内**全部 Example 实现**后才可认定没有适用参考。逐项记录已读与未读 Example；分页失败、源码或 CSS 缺失、必要上下文未取得时标记待验证并保留未读项，不能用“未发现候选”或空搜索提前结束。不要求为普通局部任务读取范围外的全部实现。

可参考源码与可直接移植分开判断。未通过移植验证、包含 Gallery 依赖或需适配的实现仍应可读并可供参考，不因缺少移植证明跳过或隐藏；直接移植须核实目标项目依赖、公开 API、环境差异及当前验证证据。来源可读只证明参考证据可用，不能证明目标行为或移植成功。相同任务内可复用有效阅读记录；目录或实现基线改变时补读受影响项，覆盖不完整时如实交付。

## 3. guidance：从任务得到可实施用法

按当前规范的相关章节核对任务是否适用、与其他表面的边界、组合和内部内容职责。需要替代方案但没有对应规范支持时，给出任务层面的选择条件并标记未覆盖，不虚构另一组件的规则或能力。

将适用规则映射到目标场景：需要哪些信息与操作、各项服务哪个决定、如何进入与结束，以及哪些能力需要调用方实现。具体布局、文案与提交行为由取得的规范、有效业务需求和真实 API 共同确定。先核实 Example 的适用范围，不能把某个案例变成所有任务的模板；找到匹配 Example 后，默认沿用其明确附加规则、结构与组件组合。

按以下依据顺序回校简报与指导：用户真正明确的要求优先；匹配 Example 的明确规则和结构作为默认实施依据，并与适用组件规范一同核对；shaping 的 AI 提案或假设只补足没有适用规范或 Example 的部分。组件规范与 Example 发生真实冲突时说明来源与影响，未解决前标记待验证，不自行宣称某方合规。精确 API 仍按真实源码核实。

回校时标清每项有影响决定的来源（用户原意、规范/Example 来源与版本、AI 提案/假设）、差异及采用理由，修正简报中被规则替代的 AI 内容，交接当前有效依据。普通方向认可不把草案全部细节变成用户明确要求；用户行为要求不自动指定界面文案。“修改后保存”只约束保存行为；若匹配 Example 的明确 Action wording 要求确认使用 “Rename”、取消使用 “Cancel”，就按该规则实施，不能因草案写了“保存”而宣称用户指定该按钮文案。此例只用于区分来源，不是内置业务规则或固定 Example 名单；实际文案与适用范围须从当前源读取。用户确实逐字指定文案时优先遵循并记录对 Example 的偏离，不虚称规则一致。

已有证据足以校正 AI 提案时直接更新并继续，不为简单任务新增简报批准、逐项确认或其他形式化关口；仅未决且影响主方案的产品取舍需要用户决定，后续必要人工 Review 保留。`source-reference` 仅表示需要适配依赖，不代表需要重新设计。

在 AaronUI-Web 工作流中由当前执行者使用该库的真实导出实现，定位目标项目已有包依赖和引用方式。核实所需 props、事件与依赖组件；不凭规范中的名称猜 API，不重造同名或仅外观相似的 Dialog，不引入外部设计生成服务作为前置依赖。目标工程未接入组件库时说明具体缺口，继续可独立完成的指导；接入依赖、跨仓修改仍沿用实际授权。

### Dialog / Sheet：初版动效接入

任务包含可交互 Dialog 或 Sheet 时，把进入与退出动画列为本次明确的交付检查项，不等到视觉润色才处理。这是本工作流的验证要求，不冒充知识服务已有组件规则；组件规范未覆盖时仍标记未覆盖，并可独立记录动效检查的观察结果。

从当前组件实现、样式入口和匹配 Example 核实动画由谁提供、如何启用，以及打开状态、Portal / presence 与退出完成后卸载的关系。指导须明确目标工程需要保留或接入的样式、状态和生命周期；若库已内置动效，优先正确接入，避免重复叠加。排查调用方条件渲染、关闭时立即清空内容或移除容器、样式遗漏/覆盖等是否截断动效；不能只写“使用真实组件，因此自带动画”。不在 Skill 固定 props、CSS 选择器、时长、缓动或位移，具体行为以当前证据为准；当前源没有可用实现时，明确缺口并在授权范围内补足调用方方案，不静默修改组件库。

交给实现者的验证计划应包含：正常动效设置下首次打开、关闭及再次打开；本次实际支持的关闭路径；内容表面及存在的遮罩；减少动态效果设置下的预期行为。生成初版后立即按下一节执行动效专项检查并修复已授权范围内问题，后续 audit 可复用未变更的有效证据，不新增人工确认关口。仅交付静态稿或静态平铺时说明动态行为尚未验证，不能据此宣称产品缺失或具备动效。

交付与任务规模相称的指导：场景与组件映射、采用理由、规范来源/章节、真实 API 依据、参考 Example 的选择理由与来源、采用/调整/不采用部分及需求差异、已读与未读项、调用方责任、必要状态与适用验证、未覆盖及待验证项。指导完成不等于已实现；用户只要求指导时到此交付，已授权实现时继续实现并用当前产物进入 audit。

## 4. audit：从现有证据得到判断

按当前规范检查适用语义、场景边界、组合、内部用法和文案；维度来自取得的正文，不在本包另建规则清单。针对相关入口和状态，以源码、可见设计和实际交互分别取证，不为局部审查运行无关全量检查。

按 guidance 的来源区分复核简报和实现，防止 AI 提案再次覆盖已匹配规则；同时检查同源附加规则的适用性与当前证据。核对实际实现与所选 Example 的关系：逐项记录本次适用的 variant、尺寸、排版、间距、状态与交互的对照事实、差异及依据；维度随任务和取得的 Example 确定，不扩展成固定组件清单或全量测试矩阵。公开 API 合法只证明组件支持该用法，不能证明符合匹配 Example，也不足以支持偏离；不能只核对导出或 props 就判通过。实现或修复完成后，对照原 Example 的实际渲染；即使没有差异，也须留下双方当前基线及实际对照证据，无法对照时标记待验证。没有完全照搬参考并非自动违例，移植证明也不能替代目标实现验证；guidance 的选择记录是交接依据，不替代本次源码与交互取证。

每个差异都须说明处理结论：按匹配 Example 对齐；依据用户明确要求或有效业务规则保留，并引用具体依据和影响；证据不足则待验证。发现应对齐的差异，在纯审查中给出最小调整建议，获准修复时完成对齐并复验。保留差异不等于符合被偏离的规则；仍按下表表达规则结论和证据范围，不新增另一套通过状态。Example 的演示简化逻辑不能覆盖有效业务规则，也不能以对齐为由删除业务约束。未覆盖或缺少所需运行证据均不算通过。

每项结论说明位置、观察事实、适用规范章节/规则、参考来源与实际差异、判断及影响；违例给最小调整建议。状态分开表达：

| 状态 | 所需依据 |
| --- | --- |
| 符合 | 规则确实适用，且有足够当前证据支持；说明静态或运行证据范围 |
| 违例 | 当前证据与适用规则冲突，能够解释对任务的影响 |
| 待验证 | 已有规则覆盖，但缺运行/业务证据或来源存在未解冲突 |
| 未覆盖 | 当前知识服务不支持对应资源或独立规则；不算符合 |
| 不适用 | 规则前提在本场景不成立，并给出理由 |

静态图不能证明提交、关闭、焦点、异步结果或上下文保留。没有观察到某行为不直接判违例；动态规则需要真实交互证据，无法操作时留待验证。技术检查、截图或一次成功操作不能证明其他状态通过。

### Dialog / Sheet：动效专项检查与修复

对本次可交互 Dialog / Sheet 的真实入口执行以下检查，初版自检与 audit 共用此方法：

- **实际过渡**：记录运行版本、入口及动态效果设置。在正常动效设置下，从关闭状态触发首次打开，观察进入过程；关闭时观察退出过程直至卸载，再次打开确认可重入。检查内容表面及存在的遮罩与当前来源/目标预期一致，退出不因父级卸载或内容提前重置而突然消失。覆盖实际支持的关闭按钮、取消、Esc、遮罩、提交成功或路由切换等路径；只检查本任务存在且允许的路径，禁止关闭的路径不强行启用。共享同一关闭生命周期的路径可复用动效证据，但须确认各入口确实进入该生命周期；不同清理逻辑单独验证。
- **动态证据**：使用可辨认时间过程的录屏或连续帧观察，必要时结合浏览器动画时间线、运行中的样式/几何变化与 DOM 生命周期取证。取证应覆盖开始、过渡和完成，不能只用打开后截图、静态 CSS 声明、非零 duration 或一次 `getAnimations()` 结果证明动效可见。不要为方便断言硬编码统一时长或要求特定动画技术。
- **环境与例外**：核实系统或浏览器的减少动态效果设置，并按当前来源/用户要求检查其降级行为；有依据的减少或取消动效不判为遗漏，自动化环境也不能默认开着该设置后宣称正常动效已通过。用户明确要求无动画时记录依据；静态画布、截图或不可操作环境只能支持静态结论，动效留待验证。恢复检查时临时改变的环境设置。
- **发现与修复**：正常设置下已观察到瞬现、瞬消或退出被截断时，记录复现路径、预期来源和动态证据，作为本次动效要求未满足的发现；只有与当前适用规则冲突时才称规则违例。先定位组件接入、样式和调用方生命周期，按现有实施授权修复；只有审查授权时交付最小修复建议。修复后重验首次进入、退出、再次打开及受影响关闭路径，同时确认关闭后的焦点恢复和背景交互限制未受破坏。缺运行证据继续标记待验证，不以代码已修改结案。

交付记录分别写清进入、退出、再次打开、关闭路径与减少动态效果的观察结果、证据位置、已修复/待验证项；没有修改或证据仍有效时复用，不无条件重跑其他组件或整条流程。

纯审查交付结论；已授权修复则只处理选定范围，验证受影响入口、状态和真实 API 使用，更新发现的实施与验证状态。指导建议、已修改和已验证分别记录。规范变更影响既有结论时重读相关章节并复核，不无故重跑整个设计流程。

## 5. 完成与交接

小任务可在会话交付；需要跨阶段追踪时复用目标项目已有报告或 `docs/design/<topic>/`，不要把业务报告写入本 Skill。至少保留模式、目标基线、规范来源/revision/章节、Example 选择/来源/差异与已读/未读记录、实现与观察证据、结论/改动、未覆盖和待验证项。

完成意味着约定范围内每个对象有适用结论或明确的覆盖/证据缺口，已授权改动和相关验证已处理。可以交付“存在未覆盖项的指导/审查”，不能称为所有组件合规或全流程通过。关键证据获取失败且核心任务无法执行时，报告具体阻塞与已完成部分。

交回 Orchestrator 或相邻 Skill 时只带报告位置、基线及受影响项。组件审查不能替代信息价值判断、流程完整性、独立任务走查或中文一致化审查，也不能跨越它们的人工 Review。后续已批准改动改变关键业务决定时同步已有设计简报；实质改变组件用法时触发局部 audit，未改变部分复用有效证据。
