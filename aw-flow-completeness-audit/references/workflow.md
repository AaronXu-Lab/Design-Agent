# 流程完整性审查工作流

本文是执行事实源，[流程图](../docs/workflow.svg) 是面向人的概览。检查约定范围内的用户流程是否对必要步骤、分支、转换和结果给出了完整设计；以已实现界面为主，兼容设计稿、原型和需求描述，不要求先写完整 PRD。

## 1. 确定任务边界与证据

沿用已有目标、范围、角色和约束，从实际入口定位目标流程。明确可观察的完成结果，例如“接收者获得指定访问权限”，不能把“发送成功”当成同一结果。局部审查只记录上游条件与下游结果，不扩张为全产品审计。

按问题追踪界面、调用方、状态逻辑和需求，不遍历整个仓库。证据各自只证明自己的范围：

- 需求或已确认决定：行为应当怎样，保留适用角色、条件和例外。
- 运行观察：本次条件下实际发生了什么，记录入口、角色、数据与环境。
- 源码：实现声明了什么；静态存在不等于用户可达或运行通过。
- 设计稿、截图、原型和描述：明确表达的设计；未展示不等于不存在。

代码不能反向证明需求。会产生提交、邀请、删除、支付等副作用的检查，只在已确认隔离的环境中做；否则用静态证据并保留验证缺口。审计阶段不修改业务代码。只有目标无法定位时才询问最小必要信息。

## 2. 建立流程及交接关系

从真实入口按“前置条件 → 操作或系统事件 → 分支条件 → 新状态与可见反馈 → 后续动作或结束结果”追踪，保持对象、角色、输入和权限等上下文连续。用项目现有表格或流程图记录，没有时按 [审计记录](audit-record.md) 建立。每个分支说明：

- 谁在什么条件下进入，哪个动作或事件触发转换；
- 作用于哪个对象，产生哪些保存、发送、权限变化等副作用；
- 用户能观察到什么，下一步由谁完成；
- 如何正常结束、取消或离开，适用时如何中断后恢复。

跨角色或跨系统追踪到真实结果；范围外环节只记录交接条件、接收方、预期结果与依赖，未核实的依赖限制端到端结论。

## 3. 按实际条件检查覆盖

先查正常路径是否缺必要步骤，再查业务上确实可能触发的其他路径。下表用于发现适用情况，不要求逐项生成状态：

| 触发条件 | 要判断的完整性问题 |
| --- | --- |
| 首次使用、无记录、无匹配结果 | 能否区分缺少前置条件与结果为空；有无适用的后续或结束方式 |
| 输入、业务校验、数量或容量限制 | 何时发现问题，如何修正，输入和选择是否保留 |
| 异步提交、后台处理、长时间等待 | 提交与最终成功是否区分；结果未知时如何确认，离开后如何找回进度 |
| 批量操作、多步写入、外部交接 | 部分成功如何呈现；已完成项与未完成项如何继续处理 |
| 网络中断、超时、会话过期 | 当前结果是否可判定；重新登录或重试是否丢失工作、重复产生副作用 |
| 多人编辑、重复操作、旧数据 | 冲突、重复提交及对象已经变化时如何处理 |
| 角色、归属、权限或资源变化 | 操作前后能力变化是否有交代；途中失去权限或对象被删除后如何结束 |
| 取消、返回、关闭、重新进入 | 中断影响、已保存内容及恢复位置是否一致；取消界面与取消后台工作是否区分 |
| 不可逆动作或明确终态 | 后果是否在决策前明确；完成结果能否确认，无法恢复时是否给出解释或后续 |

按影响和发生条件选择分支，不做笛卡尔积；只在组合会改变操作、数据、权限、副作用或结果时检查组合。优先覆盖阻断任务、丢失工作、重复写入或不可逆的情况。

重点核对相邻转换和交接：有错误页却回不到可继续的步骤、有成功提示却找不到结果、重试会重复处理已成功项，都是流程断点。每个适用路径应有可解释的后续或合法终点。不因通用清单新增产品不支持的撤销、草稿、离线或自动重试；确有需要时作为产品方案提出，说明依赖和取舍。

## 4. 区分缺口、提案与待验证

每个发现附位置或场景、进入条件、证据、影响及最小处理建议，结论使用：

- **已验证缺口**：已有要求未落实、设计内部矛盾，或真实路径出现无交代的断点。
- **待决产品规则**：依据不足以裁定业务行为；给出推荐方案、理由和必要的替代方案及代价。
- **待验证**：材料不能判断覆盖或运行结果；指出最小补充证据。
- **已覆盖 / 不适用**：记录支持证据或理由。

覆盖与严重程度分别记录，不为输出问题制造缺口。建议聚焦最小补全：补条件说明、补必要转换、保留上下文或明确终点。文案、组件选型、视觉和任务易用性不在本审查范围内，只记录交接项。

## 5. 交付审计并等待人工 Review

局部审查用短答或小表交付。完整审计按 [审计记录](audit-record.md) 保存到项目现有文档位置，没有时用 `docs/audits/<flow-name>-completeness.md`；无法保存时输出同等内容并说明。

审计完成条件：范围内入口、主路径、适用分支和关键交接已登记，每项有覆盖结论或未验证原因，事实与提案分开，报告已交付。证据不足时交付“有验证缺口的审计”，不能宣称流程完整。

**报告交付后必须停在人工 Review 关口。即使初始请求是“检查并修复”，也不能在同一阶段直接修改业务代码或正式设计。** 告知用户这是本 Skill 的强制规则。沉默、时间经过、前期笼统授权或仅认可报告判断，都不是实施授权。用户要求调整建议时先更新报告。仅审查的请求以报告交付为完成。

## 6. 人工 Review 后实施与复查

用户明确选定要实施的建议后直接实施，不重复要求批准。核对报告基线与当前实现，只补查影响本次决定的变化；新发现的产品取舍或超范围修复单独交回 Review，不阻塞已批准事项。

用与问题相称的检查验证受影响的入口、转换、结果和上下文保留；需要动态证明的行为不能只凭代码或构建成功关闭，环境不支持时记“已修改，运行待验证”。更新报告中每项的处理结果。补全改变 AaronUI-Web 组件用法时，交 `aw-component-advisor` 局部复核。批准的补全改变范围、主路径或关键规则时，同步已有设计简报与受影响图稿，标明待实施或已实施。

## 续接

审计过大时按子流程分批更新同一记录，保留稳定 ID、证据基线、已检查范围、未检查队列、未决决定和 Review 状态；续接只读相关记录和变更证据，未检查项不算通过。项目已有状态表时优先增补，不并行维护两套相同事实。
