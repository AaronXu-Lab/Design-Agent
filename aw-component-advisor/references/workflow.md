# 组件指导与审查工作流

本文是执行事实源，[workflow.svg](../docs/workflow.svg) 是人类概览。本 Skill 保存工作方法；组件规范从 AaronUI-Web 的本地知识 MCP 读取，精确 API 与行为按当前 TypeScript 实现核实，不在 Skill 中维护规范副本。

## 1. 选择模式与范围

- **guidance**：准备设计、选型或实现时，依据用户任务、当前规范和真实组件能力给出可实施的用法与验证计划。完整设计流程在塑形之后、生成初版之前执行。
- **audit**：对已有界面、设计或实现核对组件选择、组合和内部用法。完整流程在信息冗余审计之后执行；后续改动改变组件用法或约束时，只复核受影响部分。
- 混合请求先指导后审查，分别记录建议与实际证据。仅颜色、间距等视觉问题按原请求处理，不扩张为本专项。
- 旧“编辑 Reference / 同步索引”请求不是第三种模式：指出规范由 AaronUI-Web 维护，不能在本包恢复静态 Reference。若用户明确授权修改该源项目，按源仓规范完成；没有该授权时只给源位置与迁移说明。

沿用用户已给出的任务、目标工程和授权。识别本次对象、触发入口、当前状态和期望结果，以真实调用方确认组件。稳定 ID 不等于展示名或代码导出名；不能靠外形匹配。只读审查不自动授权修改产品、库组件或规范，已有具体实施授权则完成其范围内修复及验证。

## 2. 获取同一规范与能力证据

读取 [知识访问契约](knowledge-access.md)，通过 `list_documents` 定位可用资料，再用 `get_document({type: "component", id: "dialog"})` 获取本次当前正文。只读取相关章节与必要的真实源码。已经取得当前版本且没有相关变更时可在同一任务内复用；跨会话、规范变化或影响判断的实现变化后重新获取并标记基线。

guidance 与 audit 使用同一份规范。记录文档来源、revision、章节/规则引用及实现版本，报告只引用判断需要的短片段，不保存一份供下次执行使用的规范副本。历史报告保留当时证据，不能升级为当前规范。

本轮仅支持 `component/dialog`。Gallery 展示其他页面不代表 MCP 覆盖；其他组件、场景或规则请求遇到 `NOT_SUPPORTED_YET` 时记录**未覆盖**，禁止读取旧 checker、其他 Skill 的静态组件规则、历史 Gallery 文案或相似组件规则兜底。Dialog 中使用 Button、Input、ModalActions 等依赖可按真实导出和类型组合，但不声称它们获得独立规范指导或审查。

服务不可用、正文缺失、响应不能核实来源、读取失败，或资料与当前源码发生影响判断的冲突时，记录**待验证**及最小缺失证据。继续不依赖它的部分；核心判断依赖该资料时暂停相应结论，不把工具错误或空结果算成功。不擅自安装、启动服务或改客户端配置，用户已有授权时可按服务文档操作。不能用缓存或内置规则制造通过。

规范用于语义、使用条件与组合判断；当前公开 TypeScript 类型、导出和实现用于精确 props、回调、默认值与行为判断。业务决定以最新有效需求为准。来源冲突时说明冲突及影响，不静默改任何一方来制造一致；源码存在也不能证明运行行为通过。

## 3. guidance：从任务得到可实施用法

按当前规范的相关章节核对任务是否适用、与其他表面的边界、组合和内部内容职责。需要替代方案但没有对应规范支持时，给出任务层面的选择条件并标记未覆盖，不虚构另一组件的规则或能力。

将适用规则映射到目标场景：需要哪些信息与操作、各项服务哪个决定、如何进入与结束，以及哪些能力需要调用方实现。具体布局、文案与提交行为由取得的规范、有效业务需求和真实 API 共同确定；案例解释规则，不能把某个案例变成所有任务的模板。

在 AaronUI-Web 工作流中由当前执行者使用该库的真实导出实现，定位目标项目已有包依赖和引用方式。核实所需 props、事件与依赖组件；不凭规范中的名称猜 API，不重造同名或仅外观相似的 Dialog，不引入外部设计生成服务作为前置依赖。目标工程未接入组件库时说明具体缺口，继续可独立完成的指导；接入依赖、跨仓修改仍沿用实际授权。

交付与任务规模相称的指导：场景与组件映射、采用理由、规范来源/章节、真实 API 依据、调用方责任、必要状态与适用验证、未覆盖及待验证项。指导完成不等于已实现；用户只要求指导时到此交付，已授权实现时继续实现并用当前产物进入 audit。

## 4. audit：从现有证据得到判断

按当前规范检查适用语义、场景边界、组合、内部用法和文案；维度来自取得的正文，不在本包另建规则清单。针对相关入口和状态，以源码、可见设计和实际交互分别取证，不为局部审查运行无关全量检查。

每项结论说明位置、观察事实、适用规范章节/规则、判断及影响；违例给最小调整建议。状态分开表达：

| 状态 | 所需依据 |
| --- | --- |
| 符合 | 规则确实适用，且有足够当前证据支持；说明静态或运行证据范围 |
| 违例 | 当前证据与适用规则冲突，能够解释对任务的影响 |
| 待验证 | 已有规则覆盖，但缺运行/业务证据或来源存在未解冲突 |
| 未覆盖 | 当前知识服务不支持对应资源或独立规则；不算符合 |
| 不适用 | 规则前提在本场景不成立，并给出理由 |

静态图不能证明提交、关闭、焦点、异步结果或上下文保留。没有观察到某行为不直接判违例；动态规则需要真实交互证据，无法操作时留待验证。技术检查、截图或一次成功操作不能证明其他状态通过。

纯审查交付结论；已授权修复则只处理选定范围，验证受影响入口、状态和真实 API 使用，更新发现的实施与验证状态。指导建议、已修改和已验证分别记录。规范变更影响既有结论时重读相关章节并复核，不无故重跑整个设计流程。

## 5. 完成与交接

小任务可在会话交付；需要跨阶段追踪时复用目标项目已有报告或 `docs/design/<topic>/`，不要把业务报告写入本 Skill。至少保留模式、目标基线、规范来源/revision/章节、实现与观察证据、结论/改动、未覆盖和待验证项。

完成意味着约定范围内每个对象有适用结论或明确的覆盖/证据缺口，已授权改动和相关验证已处理。可以交付“存在未覆盖项的指导/审查”，不能称为所有组件合规或全流程通过。关键证据获取失败且核心任务无法执行时，报告具体阻塞与已完成部分。

交回 Orchestrator 或相邻 Skill 时只带报告位置、基线及受影响项。组件审查不能替代信息价值判断、流程完整性、独立任务走查或中文一致化审查，也不能跨越它们的人工 Review。后续已批准改动改变关键业务决定时同步已有设计简报；实质改变 Dialog 用法时触发局部 audit，未改变部分复用有效证据。
