# 独立任务走查工作流

本文是执行事实源，[../docs/workflow.svg](../docs/workflow.svg) 是面向人的概览。在独立新会话中，通过可交互原型或运行中的产品检查用户完成任务的实际体验，交付问题报告并等待人工 review。

## 1. 确定会话、需求与可操作对象

使用未参与本轮设计、实现或前置审查的新会话，首次走查不导入旧会话、组件规范或已有问题报告。当前会话已参与上述工作时，整理需求来源、原型入口和已有任务选择，供用户在新会话启动；不声称“忽略历史”就能恢复独立性，也不自行创建会话。用户明确要求在当前会话继续时可以执行，但报告注明上下文影响，不标为独立走查。

需求依据：

- 有 PRD 时可完整读取，记录版本或来源。没有时使用用户需求、任务说明或设计简报，只追问会改变任务选择或成功判定的信息。
- 设计简报只辅助任务选择和覆盖规划，权重低于用户选定任务、最新需求与实际界面。其中的路径、图稿与设计理由是待检验方案，不是标准答案；已确认业务规则仍是需求，暂用假设不能升格为约束。简报与界面不同时先记录差异，再按最新决定核实。
- 文档写明入口或路径，不代表用户能从界面发现。记录已从文档获知的关键路径提示，不能声称首次独立发现了已读过的路径。

必须能实际操作当前版本。核实入口、账号角色、平台、测试数据和允许的操作范围，使用当前环境可用的交互工具。只有静态图、工具无法操作或服务未就绪时，说明所缺条件并暂停相关走查，不降级成静态推演；环境修复不属于本 Skill。会发送真实消息、产生费用或不可逆的操作需已有明确授权，否则暂停该动作，继续其他独立任务。

## 2. 提出候选任务并由用户选择

根据需求提出少量有代表性的候选任务，覆盖主要目标、重要决策、跨页面衔接或重复工作。范围来自用户目标与需求，不只按现有导航推导，以免漏掉界面未提供的必要能力。不把异常组合或遍历控件设为任务。

每项候选包括：任务 ID、要达成的结果、起始条件、可观察的成功条件和选择理由。描述结果，不预设点击顺序，例如“将三位协作者加入指定项目，其中一位只能查看，并确认结果”。

同时提供用户类型：

| 类型 | 已知条件与检查重点 |
| --- | --- |
| A：懂业务、首次使用产品（默认推荐） | 理解业务对象和术语；不预设知道产品导航、专有操作或隐藏规则 |
| B：业务与产品新手 | 需要理解必要业务概念、术语与操作后果 |
| C：熟练用户 | 重点检查频繁操作、重复劳动、上下文切换与效率 |

请用户选定任务和类型；只选任务时采用默认 A，已有选择直接沿用。没有选定任务时不能把候选当作批准范围；任务过大时提出分批方案。不同类型分开记录知识假设和路径；同一会话后续尝试不能冒充首次体验。不虚构 persona 细节。

## 3. 从界面执行任务并记录第一次尝试

从选定起点开始，只通过用户可获得的界面、帮助和反馈寻找操作。可用可见内容和可访问性树定位控件；不得借助源码、隐藏 DOM、内部状态、网络接口或猜测路由替用户找到入口。工具能定位元素不等于用户能发现它。

开始前不巡览产品、不列标准路径、不读旧报告。沿实际看到的信息逐步操作，在关键决策处记录当前目标、可见线索、所选操作及结果；保留误入、返回、求助、重复填写和上下文丢失。

按目标用户的知识，在关键步骤检查：

1. 是否理解此时要达成什么，以及为什么需要这一步。
2. 能否发现相关操作与必要信息。
3. 操作的标签、位置与表现是否让人理解其作用和后果。
4. 操作后能否知道发生了什么、是否推进目标、是否完成。

同时判断整体负担：步骤是否有必要价值，跨页面对象与状态是否连续，是否被迫记忆或重复输入，是否有不必要的往返，结果是否满足真实目标。业务必要的审批、确认和约束不因增加步骤就成为问题。结构层面的问题只描述障碍、条件与影响，不设计新方案；与任务无关的美观偏好、状态枚举、组件规范或文案规则不展开。

## 4. 保存证据，再复现与核实

遇到问题立即保存到目标项目或用户指定的报告位置，用稳定问题 ID 关联任务和证据，不写入 Skill 目录。静态问题用截图，连续交互或状态变化用步骤截图或录像；避开账号秘密和无关个人数据。

先保留第一次尝试，再在不产生真实副作用的条件下复现；学会路径后的成功不算首次可发现性通过，不能稳定复现的保留条件与不确定性。分别表达：

- **已观察事实**：实际界面、操作、结果和证据位置。
- **设计影响判断**：这些事实为何阻碍选定用户；假设须说明。
- **待核实条件**：权限、需求冲突、数据条件或原型能力尚不能证明的部分。

首次记录完成后可回查 PRD、向用户澄清或对照已有报告，补充核实记录，不回写成“首次就已知道”；不转为读源码的实现审计。区分原型可演示行为与真实后端能力；必要步骤无法交互时报告“无法验证”。某任务受阻时记录最后可达位置和缺失条件，继续其他任务；没有新线索时停止盲试。版本或数据变化时标明新基线，只重查受影响任务。

## 5. 交付问题报告，等待人工 review

报告详略匹配范围，至少包含：

- **范围与依据**：入口与版本线索、需求来源、用户类型与已知知识、起点和数据条件、会话独立性及已知路径提示。
- **任务结果**：每项任务的实际路径与证据，标为“完成 / 完成但有障碍 / 未完成 / 无法验证”并说明原因；工具或环境阻塞不归因于设计。
- **问题记录**：问题 ID、任务和步骤、观察事实、证据引用、需求依据、影响、复现情况和未决条件。
- **人工 review 项**：需要用户判断的问题、事实冲突和验证缺口。

按任务影响区分阻断、显著负担和轻微障碍；同一原因的多处表现合并并保留各处证据。不编造情绪分数、成功率或收益。

默认只交付问题与影响，不提供修改方案，不修改产品。保存报告后等待人工 review；用户之后明确要求讨论方案或修复时，沿其选择的范围继续。局部复查只检查对应任务，不称为新的独立首次走查。

完成标准：每个选定任务有结果与证据或明确的无法验证原因，问题可定位，事实与假设分开，报告已保存并提供位置。范围内没有问题时如实说明。Agent 走查不等同于真实用户研究。
